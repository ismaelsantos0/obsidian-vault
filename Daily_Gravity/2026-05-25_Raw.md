### 1. Como verificar se o seu `.env` está exposto
Abra o navegador ou use uma ferramenta de linha de comando para tentar acessar diretamente o arquivo através da URL do seu site. Tente acessar os seguintes caminhos:
*   `https://seu-site.com/.env`

**Resultado:**
*   Se o site retornar um erro **403 Forbidden** ou **404 Not Found**, o arquivo está protegido.
*   Se o site exibir o conteúdo de texto do arquivo ou iniciar o download dele, o arquivo está exposto e as suas chaves e senhas foram comprometidas. **Se isso ocorreu, você deve alterar imediatamente todas as senhas e chaves de API contidas no arquivo.**

---

### 2. Como corrigir e proteger o arquivo `.env`

Existem três maneiras principais de corrigir essa vulnerabilidade, dependendo de como o seu servidor está configurado:

#### Solução A: Configurar a Raiz do Servidor (Web Root) - *A prática mais segura*
A forma correta de estruturar uma aplicação web é colocar apenas os arquivos públicos (como `index.html`, arquivos de imagem, CSS e JS compilados) dentro de uma pasta chamada `public` ou `dist`.
*   O arquivo `.env` deve ficar na pasta raiz do projeto, **um nível acima** da pasta `public`.
*   Configure o seu servidor web (Nginx/Apache) para apontar a raiz do domínio (Web Root) diretamente para a pasta `public`, e não para a pasta raiz do projeto. Dessa forma, é fisicamente impossível para um usuário acessar arquivos que estão fora da pasta `public` via navegador.

Exemplo de estrutura segura:
```text
meu-projeto/
├── .env                  <-- Fora da pasta pública (protegido)
├── node_modules/
├── src/
└── public/               <-- Raiz do servidor web (Web Root)
    ├── index.html
    └── assets/
```

#### Solução B: Bloquear o acesso no Nginx
Se você usa o **Nginx** como servidor web, adicione a seguinte regra no arquivo de configuração do seu site (normalmente em `/etc/nginx/sites-available/default` ou similar) dentro do bloco `server`:

```nginx
# Bloqueia o acesso a qualquer arquivo que comece com um ponto (como .env, .git, etc.)
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```
Após salvar o arquivo, recarregue as configurações do Nginx:
```bash
sudo nginx -s reload
```

#### Solução C: Bloquear o acesso no Apache (usando `.htaccess`)
Se você usa o **Apache**, crie ou edite o arquivo `.htaccess` na pasta raiz pública do seu site e adicione a seguinte diretiva:

```apache
# Bloqueia o acesso ao arquivo .env
<Files ".env">
    Order allow,deny
    Deny from all
</Files>

# Bloqueia qualquer arquivo que comece com ponto (.env, .git, etc.)
RedirectMatch 403 /\..*$
```

O erro **404 (Not Found)** exibido no console para a requisição `GET https://1go.casino/pix/callback` é um comportamento comum no desenvolvimento de webhooks e pode ocorrer por alguns motivos técnicos:

### 1. Método HTTP Incorreto (GET vs POST)
A grande maioria dos gateways de pagamento envia as notificações de confirmação (webhooks/callbacks) utilizando o método **POST** (onde os dados do pagamento vão ocultos no corpo da requisição). 
* Se você tentar acessar essa URL digitando-a diretamente no navegador ou clicando em um link comum, o navegador fará uma requisição do tipo **GET**.
* Se o back-end da aplicação estiver configurado para escutar apenas requisições **POST** naquela rota específica, o servidor não encontrará uma rota GET correspondente e retornará **404 Not Found** (ou em alguns casos, *405 Method Not Allowed*).

### 2. Parâmetros de Autenticação Ausentes
Endpoints de callback de produção frequentemente exigem chaves de autenticação ou tokens dinâmicos na URL (ex: `https://site.com/pix/callback?token=abcdef123456`) para identificar a origem e garantir que a requisição é legítima. Fazer uma requisição para a URL limpa (sem os parâmetros necessários) pode fazer com que o sistema de roteamento do back-end falhe em validar o caminho e retorne 404.

---

### Como desenvolvedores testam isso corretamente em desenvolvimento
Para depurar e validar se o fluxo de callback está funcionando sem precisar fazer testes diretamente em produção, os desenvolvedores utilizam as seguintes práticas:

1. **Simulação com POST:** Utilizam ferramentas como **Postman**, **Insomnia** ou comandos `curl` no terminal para disparar uma requisição do tipo **POST** com dados simulados para a rota de teste.
2. **Uso de Túneis Locais (ngrok):** Em vez de testar diretamente no servidor de produção, utilizam ferramentas como o **ngrok** para expor o servidor local (`localhost`) temporariamente para a internet. Isso permite que a integradora de pagamentos envie webhooks de teste diretamente para o ambiente de desenvolvimento local, onde o desenvolvedor pode depurar o código linha por linha.
